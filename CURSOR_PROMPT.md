# Промпт для Cursor

Этот файл содержит три части: правила проекта, промпт первого этапа (M0) и шаблон промпта для следующих этапов.
Источник истины по архитектуре: `ARCHITECTURE.md` в корне репозитория.

## Как пользоваться

1. Положите `ARCHITECTURE.md` в корень репозитория.
2. Создайте файл `.cursor/rules/teambot.mdc` и вставьте в него блок из раздела «Правила проекта».
3. Откройте Cursor в режиме Agent, вставьте промпт M0 и дождитесь плана и вопросов. Код пусть пишет только после вашего подтверждения плана.
4. Для следующих этапов используйте шаблон. Один этап за один запуск.

## Правила проекта

Содержимое файла `.cursor/rules/teambot.mdc`:

```
---
description: Team Bot — архитектурные правила проекта
alwaysApply: true
---

Источник истины — ARCHITECTURE.md. Если задача или код противоречат ему, остановись и задай вопрос, не импровизируй.

Архитектура
- Модульный монолит, порты и адаптеры. core/ не импортирует adapters/, web/, pipeline/, infra/.
- Названия платформ (telegram, vk, max, zoom, jitsi, telemost) встречаются только в adapters/ и bootstrap.py.
- Интерфейсы живут в core/ports.py. Новая платформа или провайдер = новый адаптер, ядро не меняется.
- Все обращения к LLM только через LLMRouter с указанием data_class. Прямые вызовы SDK провайдеров вне adapters/llm запрещены.
- Все задачи работают только через интерфейс TaskStore.

Данные
- Каждая командная таблица содержит team_id. Репозитории принимают TeamContext и сами фильтруют по команде; запросов без команды быть не должно. Row-Level Security включается на этапе M2.5.
- События идемпотентны: уникальность (platform, chat_id, message_id).

База данных (SQLite на M0–M2, затем PostgreSQL)
- Соблюдай правила DB-1…DB-15 из ARCHITECTURE.md, раздел 8.1. Нарушение этих правил считается ошибкой, даже если код работает на SQLite.
- Доступ к БД только через репозитории. Сырой SQL запрещён; диалектный код только в adapters/storage/dialect.py. Выбор БД только через DATABASE_URL.
- Идентификаторы (UUID) и время (aware UTC) создаёт приложение. Нативные ENUM, массивы, запросы по содержимому JSON и FTS5 не использовать.
- Регистронезависимый поиск и уникальность только через нормализованные колонки *_norm; сортировку текста в SQL не использовать.
- Каждое изменение схемы это миграция Alembic, проверенная на SQLite и PostgreSQL. Каждый PR проходит тесты на обеих БД.
- Планировщик и поиск по смыслу только через порты Scheduler и IdeaIndex.

Код
- Python 3.12, полная типизация, async для всего ввода-вывода.
- ruff и mypy без ошибок.
- Идентификаторы (переменные, функции, классы, таблицы, поля) на английском. Комментарии и docstring подробные и на русском (ARCHITECTURE.md, раздел 4.1): в начале модуля назначение и место в архитектуре, у каждого класса и публичной функции docstring (что делает, аргументы, результат, исключения), комментарии объясняют, зачем сделано так, а не пересказывают код.
- Тексты для пользователей бота на русском, в отдельном модуле сообщений.
- Точка входа проекта: main.py в корне; бизнес-логики в нём нет, сборка приложения в bootstrap.py.
- README.md это подробное описание функционала на русском; обновляй его в каждом этапе вместе с кодом.
- Не добавляй зависимости без необходимости; если добавляешь, объясни зачем в итоговом отчёте.

Безопасность
- Секреты только из переменных окружения. В репозитории только .env.example.
- Никогда не пиши в логи тексты сообщений, транскрипты, токены и персональные данные.

Внешние API
- Не придумывай поведение API (MAX, Телемост, Zoom, Jitsi, proxyapi.ru, GigaChat, Z.ai). Сверяйся с официальной документацией. Если не уверен, оставь явную заглушку с TODO и задай мне вопрос.

Совместимость
- Существующие slash-команды бота (/start, /add, /list, /list_csv, /list_html, /summary) не переименовывай и не ломай их поведение.
- Новые команды добавляй только через реестр core/commands.py (ARCHITECTURE.md, раздел 9.1).

Процесс
- Делай только текущий этап из ARCHITECTURE.md, раздел 15. Не реализуй будущие этапы.
- Для каждого сервиса пиши юнит-тесты с фейковыми портами; для адаптеров контрактные тесты. Перед завершением запусти ruff, mypy и pytest.
- В конце работы дай отчёт: что сделано, как запустить, что не сделано и какие вопросы остались.
```

## Промпт этапа M0 (каркас)

Вставьте в Cursor Agent целиком:

```
Ты разработчик проекта Team Bot. Сначала полностью прочитай ARCHITECTURE.md и правила проекта.
Твоя задача — этап M0 «Каркас» (раздел 15 ARCHITECTURE.md). Больше ничего не реализуй.

Шаг 1. Не пиши код. Составь план работ по пунктам ниже, перечисли файлы, которые создашь,
и задай вопросы, если в ARCHITECTURE.md есть противоречия или пробелы. Жди моего подтверждения.

Шаг 2 (после подтверждения). Сделай:

1. Проект на Python 3.12 с uv: pyproject.toml, пакет src/teambot со структурой из раздела 4,
   точка входа main.py в корне (раздел 4.1): вызывает bootstrap, режим запуска выбирается аргументом.
   Создай только то, что нужно этапу M0. Пустые модули для будущих этапов не добавляй.
2. core/events.py и core/ports.py: типы InboundEvent, OutboundMessage, Capabilities и Protocol-интерфейсы
   из раздела 6, без реализаций.
3. docker-compose.yml: сервис app (SQLite-файл в именованном томе) и профиль postgres с сервисом
   postgres (образ pgvector/pgvector:pg16) для локального прогона тестов на PostgreSQL.
   MinIO не добавляй (понадобится на M3). Файл .env.example со всеми переменными, включая DATABASE_URL.
   Для будущего reverse proxy оставь комментарий, сервис не добавляй.
4. infra/config.py на pydantic-settings; infra/logging.py на structlog так, чтобы в логи не попадали
   тексты сообщений и токены (добавь тест на это).
5. База по правилам DB-1…DB-15 (ARCHITECTURE.md, раздел 8.1): SQLAlchemy 2 async, драйверы aiosqlite
   и asyncpg, Alembic с render_as_batch=True, выбор БД только через DATABASE_URL.
   Модуль adapters/storage/dialect.py: подключение (для SQLite PRAGMA foreign_keys=ON, WAL, busy_timeout),
   тип UtcDateTime, naming_convention для MetaData, хелпер upsert с ветками для обеих БД.
   Первая миграция: teams, users, user_identities, memberships, chats, messages (раздел 8);
   team_id NOT NULL с индексом во всех командных таблицах. RLS на этом этапе не делай (этап M2.5).
6. Базовый TeamScopedRepository (принимает TeamContext и сам добавляет фильтр по team_id) и автотест
   изоляции: перебирает все таблицы с team_id из metadata и проверяет, что из контекста другой команды
   данные недоступны. Тест должен падать, если убрать фильтр из базового репозитория.
7. FastAPI-приложение с /healthz и /readyz (readyz проверяет БД).
8. Порт Scheduler и реализация на APScheduler (только in-memory job store) с одной тестовой задачей.
   Тест на фейковом репозитории: при старте планировщик перечитывает активные записи и ставит их заново,
   повторное срабатывание не дублирует действие.
9. GitHub Actions: ruff, mypy, pytest. Тесты репозиториев и миграций параметризованы SQLite и PostgreSQL
   (PostgreSQL как service container). Дополнительно: alembic upgrade head с нуля на обеих БД и alembic check.
10. README.md по структуре из раздела 4.1: назначение, что реализовано на этапе M0, конфигурация
   (все переменные .env), запуск (python main.py и docker compose), тесты (SQLite и PostgreSQL),
   миграции, структура проекта, ограничения. Весь код с подробными комментариями и docstring на русском.

Определение готовности:
- docker compose up поднимает приложение на SQLite без ошибок; docker compose --profile postgres up
  поднимает PostgreSQL для тестов;
- ruff, mypy, pytest проходят на SQLite и PostgreSQL;
- тест изоляции команд проходит;
- миграции применяются с нуля на обеих БД, alembic check не показывает расхождений;
- python main.py запускает приложение;
- README.md описывает реализованный функционал, комментарии и docstring на русском по разделу 4.1;
- адаптеры мессенджеров, встреч и LLM не реализованы (это следующие этапы).

В конце дай отчёт: что сделано, команды запуска, что не сделано, открытые вопросы.
```

## Шаблон промпта для следующих этапов

Подставьте номер этапа и название из раздела 15 `ARCHITECTURE.md`:

```
Ты разработчик проекта Team Bot. Прочитай ARCHITECTURE.md и правила проекта.
Задача — этап {M#} «{название}» из раздела 15. Критерии приёмки из таблицы этапа обязательны.
Предыдущие этапы уже реализованы; не переписывай их без необходимости.

Шаг 1. Без кода: изучи текущий репозиторий, составь план (файлы, интерфейсы, миграции, тесты),
перечисли допущения и вопросы по документации внешних API. Жди подтверждения.

Шаг 2. Реализуй план. Следуй правилам проекта (зависимости, team_id, RLS, логи без ПДн, внешние API по документации).
Не реализуй следующие этапы.

Готовность: критерии приёмки этапа выполнены, ruff, mypy и pytest проходят, README.md обновлён
(описан весь реализованный на этапе функционал), комментарии и docstring на русском по разделу 4.1.
В конце отчёт: что сделано, как проверить вручную, что не сделано, вопросы.
```

Подсказки по этапам:

- **M1 Ядро и Telegram.** Набор slash-команд и права зафиксированы в `ARCHITECTURE.md`, раздел 9.1. Уже работающие команды (`/start`, `/add`, `/list`, `/list_csv`, `/list_html`, `/summary`) должны остаться совместимыми. Покажите Cursor код текущего прототипа и попросите в плане указать, что из него переиспользуется, а что переписывается. Если данные прототипа лежат в SQLite, попросите предложить их перенос в схему из раздела 8.
- **M2 LLM.** Дайте Cursor актуальные адреса и названия моделей из документации ваших провайдеров, в репозиторий они не зашиты. Ключи в `.env`.
- **M2.5 Переход на PostgreSQL.** План в `ARCHITECTURE.md`, раздел 8.2. Перед запуском сделайте копию SQLite-файла и сначала прогоните скрипт переноса в режиме dry-run на копии. Попросите Cursor в плане перечислить места, где код нарушает правила DB-1…DB-15; их исправляют до переноса.
- **M3 Встречи.** Перед стартом уточните, есть ли GPU. От этого зависит модель faster-whisper.
- **M4 Jitsi.** Начинайте со спайка и записи решения в `docs/adr/`, а код после него.
- **M6 MAX.** Попросите Cursor сначала сверить требования к регистрации бота и возможности API с официальной документацией.
